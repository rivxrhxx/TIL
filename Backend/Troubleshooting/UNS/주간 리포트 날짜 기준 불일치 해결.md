# UNS 주간 리포트 날짜 기준 불일치 해결

> 같은 기준일을 전달해도 주간 리포트 API들의 집계 기간이 달랐다. 서울 시간 기준 **입력 날짜가 속한 월요일~일요일**로 통일하고, 주간 범위 계산을 공통 객체로 분리했다.

## 문제 상황

취업 시장 리포트 화면에서 함께 보여주는 지표들이 서로 다른 날짜 범위를 계산하고 있었다.

| API | 수정 전 기준 |
| --- | --- |
| `weekly-collected-count` | 입력 날짜가 속한 주의 월~일 |
| `max-increase`, `max-decrease` | 입력 날짜가 속한 주의 월~일 |
| `popular-tech-stack`의 `WEEK` | 입력 날짜까지 최근 7일 |
| `tech-mentions` | 입력 날짜까지 최근 7일 |

예를 들어 `base_date=2026-09-23`(수요일)이면 앞의 API들은 **9/21~9/27**, 뒤의 API들은 **9/17~9/23**을 집계한다. 같은 화면의 ‘이번 주’가 다른 기간을 의미하고, 전주 비교 구간도 달라진다.

이 문제는 코드의 날짜 계산식과 화면 요구사항을 대조해 확인했다. 운영 데이터로 불일치 수치를 재현하거나 장애 규모를 측정한 것은 아니다.

## 원인

각 서비스가 날짜 계산을 따로 구현하면서 ‘주간’의 정의가 달라졌다.

```java
// 입력 날짜가 속한 달력상의 주
baseDate.with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY));

// 입력 날짜까지 최근 7일
baseDate.minusDays(6);
```

두 방식 모두 7일을 다루지만 시작일이 다르다. 입력 날짜가 일요일이면 두 범위가 같으므로 일요일 예시만으로는 문제를 발견하기 어렵다.

## 해결 기준

- 시간대는 `Asia/Seoul`로 통일한다.
- 이번 주는 `[월요일 00:00, 다음 월요일 00:00)`이다.
- 비교 대상은 `[지난주 월요일 00:00, 이번 주 월요일 00:00)`이다.
- 시작은 포함하고 종료는 제외한다.
- 같은 주 안의 날짜는 같은 조회 범위로 변환한다. 이후 데이터가 바뀌면 조회 결과 자체는 달라질 수 있다.
- 진행 중인 주도 일요일까지 범위를 잡되, 집계 결과는 해당 범위에 실제 저장된 데이터에 따른다.
- `popular-tech-stack`의 `MONTH` 옵션은 기존 최근 30일 기준을 유지한다.

종료를 일요일 23:59:59로 설정하지 않고 다음 월요일 00:00을 제외하면, 초 이하 정밀도의 데이터 누락과 인접 주 사이의 중복 집계를 방지할 수 있다.

## 구현

`domain/report/domain/ReportWeek.java`를 추가했다.

```java
public record ReportWeek(
        OffsetDateTime previousStart,
        OffsetDateTime currentStart,
        OffsetDateTime currentEnd
) {
    private static final ZoneId SEOUL = ZoneId.of("Asia/Seoul");

    public static ReportWeek from(LocalDate baseDate) {
        OffsetDateTime start = baseDate
                .with(TemporalAdjusters.previousOrSame(DayOfWeek.MONDAY))
                .atStartOfDay(SEOUL)
                .toOffsetDateTime();
        return new ReportWeek(start.minusWeeks(1), start, start.plusWeeks(1));
    }
}
```

`previousOrSame(MONDAY)`는 월요일이면 그대로 사용하고 다른 요일이면 직전 월요일로 이동한다.

| 변경 파일 | 적용 내용 |
| --- | --- |
| `ReportWeek.java` | 전주 시작·현재 주 시작·현재 주 종료 공통 계산 |
| `PopularTechStackReportService.java` | `WEEK`에 공통 범위 적용, `MONTH` 유지 |
| `TechMentionQueryService.java` | 최근 7일 계산을 공통 범위로 교체 |
| `WeeklyCollectedPostingCountService.java` | 기존 월~일 계산을 공통 객체로 대체 |
| `WeeklyTechTrendCalculator.java` | 최대 상승·하락 API의 비교 기간 공통화 |

서비스에서는 다음과 같이 사용한다.

```java
ReportWeek week = ReportWeek.from(baseDate);
reportQueryRepository.findTechMentions(
        week.previousStart(),
        week.currentStart(),
        week.currentEnd(),
        TECH_MENTION_LIMIT
);
```

Repository는 이미 `>= start`, `< end` 조건을 사용하므로 날짜 인자만 맞췄다. 컨트롤러 요청 파라미터와 응답 구조는 변경하지 않았다.

공고 수는 기존대로 `collected_at`, 기술 통계는 `posted_at`을 사용한다. 이번 수정은 **조회 기간의 경계**를 통일한 것이며, 집계 대상 날짜 컬럼까지 동일하게 만든 것은 아니다.

## 검증

실제 수행한 검증:

- Java 21 환경에서 `./gradlew compileJava --no-daemon` 성공.
- `git diff --check` 통과.
- 코드에서 주간 서비스들의 공통 객체 사용과 Repository의 종료 경계 제외 조건 확인.
- 요청에 따라 테스트 코드는 추가하지 않았다. 실제 DB를 통한 API 호출 검증은 수행하지 않았다.

다음은 추가 수동 검증에 사용할 **기대 범위**이며 실행 결과는 아니다. 시각은 모두 서울 시간이다.

| 입력 날짜 | 이번 주 시작(포함) | 이번 주 종료(제외) |
| --- | --- | --- |
| 2026-09-21 월요일 | 9/21 00:00 | 9/28 00:00 |
| 2026-09-23 수요일 | 9/21 00:00 | 9/28 00:00 |
| 2026-09-27 일요일 | 9/21 00:00 | 9/28 00:00 |
| 2026-09-28 월요일 | 9/28 00:00 | 10/5 00:00 |
| 2027-01-01 금요일 | 2026-12-28 00:00 | 2027-01-04 00:00 |

추가 확인 항목:

- [ ] 월요일 시작 시각의 데이터가 현재 주에 포함되는지.
- [ ] 다음 월요일 시작 시각의 데이터가 현재 주에서 제외되는지.
- [ ] 전공 필터 유무에 관계없이 동일한 주간 경계를 사용하는지.
- [ ] `MONTH` 조회가 기존 30일 범위를 유지하는지.

## 배운 점

‘주간’이라는 용어만으로는 최근 7일인지 달력상의 한 주인지 알 수 없다. 통계 API는 기간의 의미, 시간대, 경계 포함 여부를 명확히 정의해야 한다.

각 서비스에 날짜 계산을 복사하면 같은 화면의 지표도 서로 다른 기준을 갖게 될 수 있다. 이번에는 주간 범위를 작은 값 객체로 공통화해 날짜 정책을 한곳에서 관리하도록 개선했다.
